## 1. GitHub CLI Authentication Commands

### 1.1 `gh auth login`

**Purpose:** Authenticate with a GitHub host.

**Source:** https://cli.github.com/manual/gh_auth_login

**Key Behaviors:**

- **Default hostname:** `github.com` (can be overridden with `--hostname` flag)
- **Default mode:** Web-based OAuth browser flow
  - Generates OAuth token with requested scopes
  - Stores token in system credential store (or plain text fallback)
  - Location shown via `gh auth status`
- **Token input:** `--with-token` flag reads PAT from stdin
  - Minimum required scopes for classic PAT: `repo`, `read:org`, `gist`
  - **Warning:** Fine-grained PATs via `--with-token` can cause "confusing behaviour" - documentation recommends using `GH_TOKEN` environment variable instead
- **Git protocol:** `--git-protocol` sets protocol (ssh/https) for ALL users on that host (per-host, not per-account)
- **Storage:** `--insecure-storage` forces plain text instead of credential store

**Examples:**
```bash
gh auth login                                    # Interactive
gh auth login --hostname enterprise.internal    # Enterprise
gh auth login --with-token < mytoken.txt       # Token from file
```

### 1.2 `gh auth logout`

**Purpose:** Remove local authentication configuration for an account.

**Source:** https://cli.github.com/manual/gh_auth_logout

**Key Behaviors:**

- Only removes **local** configuration
- Does **NOT** revoke tokens on GitHub's server
- Supports `--hostname` and `--user` flags to specify which account
- To revoke tokens server-side: Visit https://github.com/settings/applications → GitHub CLI → Revoke Access
  - **This revokes ALL tokens ever generated by gh across ALL devices**

**Examples:**
```bash
gh auth logout                                          # Interactive prompt
gh auth logout --hostname enterprise.internal --user monalisa
```

### 1.3 `gh auth status`

**Purpose:** Display active account and authentication state on each known GitHub host.

**Source:** https://cli.github.com/manual/gh_auth_status

**Key Behaviors:**

- Shows **all authenticated accounts** and **active account** per host
- Tests authentication state for each account
- Exit code 1 if any account has auth issues (except with `--json` which always exits 0)
- `--show-token` displays actual token values
- `--active` flag shows only active account
- JSON output available via `--json hosts`

**Examples:**
```bash
gh auth status                                   # All hosts and accounts
gh auth status --active --hostname github.com   # Active account only
gh auth status --show-token                     # Include token values
```

### 1.4 `gh auth switch`

**Purpose:** Change the active account for a GitHub host.

**Source:** https://cli.github.com/manual/gh_auth_switch

**Key Behaviors:**

- Changes which account is used when targeting a host
- If host has exactly 2 accounts: switches automatically
- If host has >2 accounts: requires `--user` flag or interactive prompt
- This is a **global state mutation** - affects all gh commands system-wide

**Examples:**
```bash
gh auth switch                                          # Interactive
gh auth switch --hostname enterprise.internal --user monalisa
```

### 1.5 `gh auth token`

**Purpose:** Output authentication token for an account.

**Source:** https://cli.github.com/manual/gh_auth_token

**Key Behaviors:**

- Without `--hostname`: uses default host
- Without `--user`: uses active account for that host
- Outputs raw token to stdout

**Examples:**
```bash
gh auth token                                    # Default host, active account
gh auth token --hostname github.com --user alice
```

### 1.6 `gh auth setup-git`

**Purpose:** Configure git to use GitHub CLI as credential helper.

**Source:** https://cli.github.com/manual/gh_auth_setup-git

**Key Behaviors:**

- Configures git credential helper for authenticated hosts
- By default: configures ALL authenticated hosts
- With `--hostname`: configures single host only
- Fails if host not authenticated (unless `--force` used with `--hostname`)
- Reference: https://git-scm.com/docs/gitcredentials

**Examples:**
```bash
gh auth setup-git                                # All authenticated hosts
gh auth setup-git --hostname enterprise.internal # Single host
```

### 1.7 `gh auth refresh`

**Purpose:** Expand or fix permission scopes for stored credentials.

**Source:** https://cli.github.com/manual/gh_auth_refresh

**Key Behaviors:**

- Operates on **active account** only
- `--scopes`: Add scopes (maintains existing if not specified)
- `--remove-scopes`: Remove scopes (idempotent, cannot remove minimum set: `repo`, `read:org`, `gist`)
- `--reset-scopes`: Reset to default minimum scopes
- **Multi-account limitation:** Must `gh auth switch` to inactive account first, then switch back
- OAuth flow reference: https://docs.github.com/en/developers/apps/building-oauth-apps/scopes-for-oauth-apps/

**Examples:**
```bash
gh auth refresh --scopes write:org,read:public_key
gh auth refresh --remove-scopes delete_repo
gh auth refresh --reset-scopes
```

## 2. Multi-Account Support in GitHub CLI

**Sources:** 
- https://cli.github.com/manual/gh_auth_status
- https://cli.github.com/manual/gh_auth_switch

### 2.1 How Active Account Works

- **Per-host active account:** Each host (github.com, enterprise.internal, etc.) has ONE active account
- **Global state:** Active account is stored in gh configuration, affects all gh commands system-wide
- **Switching:** `gh auth switch` changes active account globally
- **Command behavior:** All gh commands use active account for target host unless overridden by environment variables

### 2.2 Multiple Accounts Per Host

**Confirmed:** GitHub CLI supports multiple authenticated accounts per host.

**Evidence:**
- `gh auth status` lists all accounts and indicates which is active
- `gh auth switch` provides interactive prompt when >2 accounts exist
- `gh auth token --user <username>` can retrieve tokens for non-active accounts

**Unknown:** 
- ❓ No documentation found on internal data structure for storing multiple accounts
- ❓ No explicit limit on number of accounts per host mentioned

### 2.3 Host Determination

**Sources:**
- https://cli.github.com/manual/gh_help_environment
- https://cli.github.com/manual/gh_auth_login

**Host Resolution Order:**

1. Command-specific `--hostname` flag
2. `GH_HOST` environment variable
3. Git remote URL in local repository context
4. Default: `github.com`

**Host Types:**

- **github.com:** Default public GitHub
- **Subdomain of ghe.com:** Treated as github.com equivalent for token env vars
  - Source: https://cli.github.com/manual/gh_help_environment
  - `GH_TOKEN`/`GITHUB_TOKEN` apply to "either github.com or a subdomain of ghe.com"
  - **ghe.com pattern:** GitHub Enterprise Cloud with data residency uses `<subdomain>.ghe.com`
    - Source: https://docs.github.com/en/enterprise-cloud@latest/admin/data-residency/about-github-enterprise-cloud-with-data-residency
- **Other hostnames:** Treated as GitHub Enterprise Server (GHES)
  - Use `GH_ENTERPRISE_TOKEN`/`GITHUB_ENTERPRISE_TOKEN`
  - Minimum GHES version: 2.20+ (source: https://cli.github.com/manual/)

## 3. Credential Storage

**Source:** https://cli.github.com/manual/gh_auth_login

### 3.1 Storage Mechanisms

**Priority Order:**

1. **System credential store** (preferred)
   - macOS: Keychain
   - Windows: Windows Credential Manager
   - Linux: libsecret/secret-service
   - **Unknown:** ❓ Exact credential store implementation details not documented

2. **Plain text fallback**
   - Used when credential store unavailable or fails
   - Location shown by `gh auth status`
   - Can be forced with `--insecure-storage` flag

### 3.2 Configuration Directory

**Source:** https://cli.github.com/manual/gh_help_environment

**`GH_CONFIG_DIR` Resolution (in precedence order):**

1. `$GH_CONFIG_DIR` environment variable
2. `$XDG_CONFIG_HOME/gh` (if `$XDG_CONFIG_HOME` is set)
3. `$AppData/GitHub CLI` (Windows, if `$AppData` is set)
4. `$HOME/.config/gh` (default)

### 3.3 Configuration Structure

**Unknown:** 
- ❓ No official documentation found for `hosts.yml` format
- ❓ Internal structure of credential storage not documented in primary sources
- ❓ How multiple accounts per host are stored internally not documented

**Note:** While `gh auth status` mentions "stored location", detailed file format is not in official documentation.

## 4. Environment Variable Precedence

**Source:** https://cli.github.com/manual/gh_help_environment

### 4.1 Authentication Token Variables

**For github.com and *.ghe.com:**

Precedence order:
1. `GH_TOKEN`
2. `GITHUB_TOKEN`
3. Stored credentials (from credential store or config)

**For GitHub Enterprise Server (other hostnames):**

Precedence order:
1. `GH_ENTERPRISE_TOKEN`
2. `GITHUB_ENTERPRISE_TOKEN`
3. Stored credentials

**Critical Behavior:**
> "Setting this avoids being prompted to authenticate and **takes precedence over previously stored credentials**"

**Unknown:**

- ❓ Exact interaction between `GH_HOST` and token environment variables

### 4.2 Other Relevant Variables

- **`GH_HOST`:** Specify hostname when not provided or inferrable from git context
  - If host previously authenticated: stored credentials used
  - If not authenticated: requires `GH_TOKEN` or `GH_ENTERPRISE_TOKEN`
- **`GH_CONFIG_DIR`:** Override configuration directory location

## 5. Types of GitHub Tokens

### 5.1 Personal Access Tokens (Classic)

**Sources:**
- https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens
- https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps

**Characteristics:**

- **Scopes:** OAuth-style broad scopes (e.g., `repo`, `user`, `read:org`, `gist`)
- **Access:** Can access ALL repositories user has access to
- **Minimum scopes for gh CLI:** `repo`, `read:org`, `gist`
  - Source: https://cli.github.com/manual/gh_auth_login
  - `gh auth refresh` cannot remove these minimum scopes
- **GitHub recommendation:** Use fine-grained PATs instead
- **Scope hierarchy:** Scopes like `user` include `user:email` and `user:follow`
  - Source: https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps

**Key Scopes:**

| Scope | Description | Source |
|-------|-------------|--------|
| `repo` | Full access to public/private repos, org resources, projects, webhooks | [OAuth scopes doc](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps) |
| `read:org` | Read-only org membership, org projects, team membership | [OAuth scopes doc](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps) |
| `gist` | Write access to gists | [OAuth scopes doc](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps) |
| `user` | Read/write profile info, includes `user:email` and `user:follow` | [OAuth scopes doc](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps) |
| `workflow` | Add/update GitHub Actions workflow files | [OAuth scopes doc](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps) |

### 5.2 Fine-Grained Personal Access Tokens

**Sources:**
- https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens
- https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens

**Characteristics:**

- **Permissions:** Granular, repository-specific permissions
- **Access:** Limited to single user/organization, specific repositories
- **Limit:** 50 fine-grained tokens per user
- **Org approval:** Organizations can require approval for fine-grained PATs
- **Recommendation:** GitHub recommends fine-grained PATs over classic

**CLI Usage Warning:**
- `gh auth login --with-token` with fine-grained PAT: "may cause confusing behaviour"
- **Recommended:** Use `GH_TOKEN` environment variable instead
- Source: https://cli.github.com/manual/gh_auth_login

**Current Limitations (GitHub roadmap items):**

Source: https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens

Fine-grained PATs **CANNOT**:
- Contribute to public repos where user is not a member
- Work as outside/repository collaborator
- Access multiple organizations simultaneously
- Access internal enterprise resources
- Call enterprise management APIs
- Access GitHub Packages
- Call Checks API
- Access user-owned Projects (classic)

### 5.3 OAuth Tokens from `gh auth login`

**Source:** https://cli.github.com/manual/gh_auth_login

**Characteristics:**

- Generated via web browser OAuth flow (device flow or web flow)
- Uses OAuth scopes (like classic PAT)
- Default scopes: `repo`, `read:org`, `gist`
- Additional scopes via `--scopes` flag or `gh auth refresh`
- **Token limits:** 10 tokens per user/application/scope combination
  - Source: https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps
  - Oldest revoked when limit exceeded
  - Rate limit: 10 tokens/hour (triggers re-auth prompt, no automatic revocation)

**User Modification:**
- Users can edit granted scopes to be less than requested
- Users can modify scopes after OAuth flow completes
- Application must check `X-OAuth-Scopes` header to verify granted scopes
- Source: https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps

### 5.4 GitHub App Tokens

**Sources:**
- https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app
- https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app

**Types:**

**5.4.1 JWT (JSON Web Token)**
- Used to authenticate as the GitHub App itself
- Required to generate installation access tokens
- Generated from app's private key
- Used for app-level API operations

**5.4.2 Installation Access Token**
- Generated from JWT via `/app/installations/{installation_id}/access_tokens`
- **Expiration:** 1 hour
- **Permissions:** Scoped to app's granted permissions and specified repositories (max 500)
- Can be further restricted via `repositories`/`repository_ids` parameters
- Can be further restricted via `permissions` parameter
- Works with both REST and GraphQL APIs
- Source: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app

**Unknown:**
- ❓ How GitHub CLI interacts with GitHub Apps (if at all) not documented in auth docs
- ❓ Whether `gh` can use GitHub App installation tokens not explicitly documented

## 6. Git Credential Helper Integration

### 6.1 Git Credential Helper Protocol

**Source:** https://git-scm.com/docs/gitcredentials

**Protocol Overview:**

Git credential helpers are external programs that:
- Store and retrieve credentials from long-term storage
- Communicate via stdin/stdout
- Receive one operation argument: `get`, `store`, or `erase`

**Input/Output Format:**

Key-value pairs, one per line:
```
protocol=https
host=github.com
username=user
password=token
```

**Operations:**

1. **`get`:** Return matching credentials
   - Helper reads attributes from stdin
   - Outputs credentials to stdout (subset or none if no match)
   - Can output `quit=true` to prevent prompting/other helpers
   
2. **`store`:** Store credentials (output ignored)

3. **`erase`:** Remove credentials (output ignored)

**Configuration:**

```bash
git config credential.helper foo  # Invokes git-credential-foo
```

Git prepends `git-credential-` to helper name (unless absolute path or starts with `!`).

### 6.2 How `gh` Implements Credential Helper

**Source:** https://cli.github.com/manual/gh_auth_setup-git

**Setup:**

`gh auth setup-git` configures git to use gh as credential helper for authenticated hosts.

**Unknown:**
- ❓ Exact command name git uses to invoke gh credential helper not documented
  - Likely `gh` itself or a subcommand
  - Standard would be `git-credential-gh` but not confirmed in docs
- ❓ How gh determines which account to return when called as credential helper
  - Likely uses active account for host
  - No documentation on per-directory account selection
- ❓ Whether gh credential helper respects environment variables (`GH_TOKEN`, `GH_CONFIG_DIR`)
- ❓ How gh credential helper handles multiple accounts per host
- ❓ Whether `useHttpPath` git config affects gh credential helper behavior

**Critical Gap:** No official documentation exists for `gh` credential helper protocol behavior.

### 6.3 Git Credential Context Matching

**Source:** https://git-scm.com/docs/gitcredentials

Git matches credentials by **URL context:**

```
[credential "https://example.com"]
    username = foo
```

**Matching Rules:**
- Protocol must match exactly
- Hostname must match exactly (no subdomain matching)
- Path matching: config path must be prefix of request path
- Wildcards supported in domain patterns

**`useHttpPath` Setting:**

By default, git DOES NOT consider path component for credential matching.
- `credential.useHttpPath = true`: Match credentials per-path
- Example: `https://example.com/foo.git` vs `https://example.com/bar.git` would use different credentials

**Unknown:**
- ❓ Whether `gh` credential helper respects `useHttpPath` setting not documented

## 7. Using Specific Account Without Mutating Global State

**Sources:** Research findings from environment variable documentation

### 7.1 Environment Variable Approach

**Confirmed Method:**

Set `GH_TOKEN` (or `GH_ENTERPRISE_TOKEN`) to override stored credentials:

```bash
GH_TOKEN=ghp_... gh pr list
```

This:
- ✅ Does NOT mutate global active account
- ✅ Takes precedence over stored credentials
- ✅ Works for single command invocation
- ⚠️ Requires managing raw token values

**For Fine-Grained PATs:** Recommended approach per documentation
- Source: https://cli.github.com/manual/gh_auth_login

### 7.2 `GH_CONFIG_DIR` Approach

**Theory (Not Explicitly Documented):**

```bash
GH_CONFIG_DIR=/path/to/account1/config gh pr list
```

**Expected Behavior:**
- gh would read configuration from different directory
- Could maintain separate active accounts per config dir
- Would need separate `gh auth login` per config dir

**Unknown:**
- ❓ Not explicitly documented as supported use case
- ❓ Whether all gh state is contained in `GH_CONFIG_DIR`
- ❓ Whether credential store is scoped per config dir
- ❓ Whether git credential helper integration is affected

### 7.3 Limitations

**Global Mutation Points:**

1. **`gh auth switch`:** Always mutates global active account
2. **`gh auth setup-git`:** Writes to git global/local config (depending on context)
3. **Credential store:** System-wide (keychain/credential manager)

**No Per-Directory Account Selection:**

- No built-in mechanism for directory-scoped account selection
- No `gh` equivalent to git's `.git/config` per-repository settings
- Environment variables are current best option but require external wrapper

## 8. Enterprise and github.com Coexistence

**Sources:**
- https://cli.github.com/manual/gh_help_environment
- https://cli.github.com/manual/
- https://docs.github.com/en/enterprise-cloud@latest/admin/data-residency/about-github-enterprise-cloud-with-data-residency

### 8.1 Host Classification

**github.com equivalent:**
- `github.com`
- `*.ghe.com` (Enterprise Cloud with data residency subdomains)
- Uses `GH_TOKEN`/`GITHUB_TOKEN`

**GHES (GitHub Enterprise Server):**
- All other hostnames
- Minimum version: 2.20+
- Uses `GH_ENTERPRISE_TOKEN`/`GITHUB_ENTERPRISE_TOKEN`

### 8.2 Configuration

**Per-Host Settings:**

```bash
gh config set git_protocol ssh --host github.com
gh config set git_protocol https --host enterprise.internal
```

Each host maintains:
- Git protocol setting (affects ALL users on that host)
- Multiple authenticated accounts
- One active account

### 8.3 Coexistence Scenarios

**Authenticated to Multiple Hosts:**

```bash
gh auth login --hostname github.com
gh auth login --hostname enterprise.internal
gh auth status  # Shows both
```

**Switching Context:**

1. Via hostname flag: `gh pr list --hostname enterprise.internal`
2. Via `GH_HOST`: `GH_HOST=enterprise.internal gh pr list`
3. Via git remote context: `gh` detects from local git remote

**Potential Issues:**

- Different accounts on github.com vs enterprise may have different scopes
- Git credential helper configuration may need host-specific setup
- Token environment variables (`GH_TOKEN` vs `GH_ENTERPRISE_TOKEN`) must match host type

## 9. Leak Scenarios with Multiple Accounts

### 9.1 Active Account Leakage

**Scenario:** User expects account A but gh uses account B

**Causes:**
1. Global active account was switched: `gh auth switch` mutates globally
2. Wrong `GH_CONFIG_DIR` in environment
3. Token environment variable overriding (unexpected `GH_TOKEN` in shell)

**Impact:**
- API operations execute as wrong user
- Git credential helper provides wrong token
- Commits/PRs created under wrong account
- Potential access to wrong organization's resources

### 9.2 Git Credential Helper Leakage

**Scenario:** Git operations use wrong account's credentials

**Causes:**
1. `gh auth setup-git` configures gh for all authenticated hosts
2. Git invokes gh credential helper which returns active account's token
3. No per-repository credential selection

**Impact:**
- Git push/pull/clone uses wrong account
- Commits attributed to wrong user if email not configured
- Access denied errors if active account lacks repository access

### 9.3 Environment Variable Leakage

**Scenario:** `GH_TOKEN` persists in shell, affects unintended commands

**Causes:**
1. `export GH_TOKEN=...` in shell rc files
2. Long-running shell sessions
3. Nested shell invocations inheriting environment

**Impact:**
- All gh commands use token despite stored credentials
- Different account than expected
- Token may be for different host (github.com vs enterprise)

### 9.4 Configuration Directory Confusion

**Scenario:** Wrong `GH_CONFIG_DIR` points to different account's config

**Causes:**
1. Multiple config directories for different accounts
2. Wrong directory in environment or default XDG path
3. Shared home directory or config directory

**Impact:**
- Reading wrong account's active account setting
- Wrong credentials used
- Authentication errors if host not authenticated in that config

### 9.5 Token Scope Insufficiency

**Scenario:** Active account's token lacks required scopes

**Causes:**
1. Different accounts have different OAuth scopes
2. Switching accounts doesn't validate scope requirements
3. Organization-specific scope requirements (e.g., SSO)

**Impact:**
- API operations fail with 403/404 errors
- Confusing "not found" errors (actually permission denied)
- Silent failures or incomplete data

### 9.6 Host Misclassification

**Scenario:** Host incorrectly classified as github.com vs GHES

**Causes:**
1. `.ghe.com` subdomain treated as github.com equivalent
2. Wrong token environment variable used (`GH_TOKEN` vs `GH_ENTERPRISE_TOKEN`)
3. Custom GHES on `*.github.com` domain (if possible)

**Impact:**
- Wrong token environment variable checked
- Authentication failures
- Using github.com credentials on enterprise or vice versa

## 10. What `acct` Must Wrap/Override

### 10.1 Core Requirements

To safely manage directory-scoped accounts, `acct` must:

**1. Isolate Configuration:**
- ✅ Set `GH_CONFIG_DIR` per directory/account
- ✅ Maintain separate `gh auth login` state per account
- ✅ Prevent accidental global active account mutation

**2. Provide Token Directly:**
- ✅ Use `GH_TOKEN`/`GH_ENTERPRISE_TOKEN` to override stored credentials
- ✅ Retrieve token via `gh auth token --user <user> --hostname <host>`
- ✅ Avoid relying on active account concept

**3. Wrap All `gh` Commands:**
- ✅ Intercept `gh` invocations
- ✅ Inject appropriate environment variables
- ✅ Prevent `gh auth switch` from being called directly

**4. Wrap Git Credential Helper:**
- ⚠️ **Critical:** Git will invoke `gh` directly for credentials
- ✅ Must intercept git credential helper calls
- ✅ Options:
  - Replace git credential helper config to call `acct` wrapper
  - Implement own credential helper that calls `gh auth token`
  - Override `PATH` to intercept `gh` invocation

### 10.2 Commands to Wrap/Block

**Block/Wrap for Safety:**

| Command | Reason | Acct Action |
|---------|--------|-------------|
| `gh auth switch` | Mutates global state | Block or warn, provide account-scoped alternative |
| `gh auth login` | Creates global account | Redirect to account-scoped config dir |
| `gh auth logout` | Removes from global config | Redirect to account-scoped config dir |
| `gh auth refresh` | Modifies active account scopes | Redirect to account-scoped config or use token |
| `gh auth setup-git` | Modifies global git config | Block or manage per-directory git config |
| `gh auth status` | Shows global state | Provide account-scoped view |
| `gh auth token` | Safe - can specify user | Wrap to inject --user flag |

**Safe to Pass Through (with env vars):**

All other `gh` commands safe if:
- `GH_TOKEN` set correctly, OR
- `GH_CONFIG_DIR` points to account-specific config
- `GH_HOST` set if needed

### 10.3 Git Integration Challenges

**Problem:** Git directly invokes credential helper, bypassing `acct` wrapper.

**Solutions:**

**Option A: Custom Credential Helper**
```bash
# acct sets in .git/config:
[credential "https://github.com"]
    helper = "acct-credential-helper github.com alice"
```

`acct-credential-helper` script:
- Receives git credential protocol input
- Determines account from directory context
- Calls `gh auth token --hostname <host> --user <user>`
- Returns in git credential format

**Option B: PATH Manipulation**
```bash
# acct creates wrapper script at ~/.acct/<account>/bin/gh
# Sets PATH to prioritize this wrapper
# Wrapper injects GH_TOKEN before calling real gh
```

**Option C: Replace `gh` in git config**
```bash
[credential "https://github.com"]
    helper = "!f() { GH_TOKEN=$(acct-get-token github.com) gh credential-fill \"$@\"; }; f"
```

**Unknown:**
- ❓ Whether gh has a documented credential helper subcommand
- ❓ Whether gh reads environment variables when invoked as credential helper

❓ **No documentation on internal storage format (hosts.yml)**  
❓ **No documentation on how gh credential helper selects account**  
❓ **No documentation on whether credential helper respects environment variables**  
❓ **No documentation on per-directory or per-repository account selection**  
❓ **No documentation on credential store scope with multiple config dirs**  
❓ **No documentation on whether useHttpPath affects gh credential helper**  
❓ **No explicit limit on number of accounts per host**  

### 11.3 Risks for `acct` Tool

**High Risk:**
1. Git credential helper may bypass `acct` wrapper entirely
2. System credential store shared across all config directories
3. No atomic way to ensure directory-scoped account selection
4. `gh auth setup-git` may interfere with `acct` git config

**Medium Risk:**
1. Token environment variables may leak across commands
2. Users may accidentally run raw `gh` commands
3. Multiple `GH_CONFIG_DIR` values may cause confusion
4. Different accounts may have incompatible scopes

**Low Risk:**
1. Token expiration (OAuth tokens don't expire, PATs can)
2. Account authentication state changes
3. Network connectivity issues per account

### 11.4 Recommendations for `acct`

**Must Have:**
1. Isolate `GH_CONFIG_DIR` per account
2. Use `GH_TOKEN` for command execution when possible
3. Implement custom git credential helper that respects directory context
4. Block/wrap dangerous commands (`gh auth switch`, etc.)
5. Provide clear UX for which account is active in current directory

**Should Have:**
1. Cache tokens to avoid repeated `gh auth token` calls
2. Validate token scopes before use
3. Detect and warn about environment variable leakage
4. Test credential helper integration thoroughly
5. Document known limitations clearly

**Nice to Have:**
1. Per-directory config file (`.acct-account`)
2. Interactive account selection if ambiguous
3. Token refresh/renewal support
4. Integration with other git hosting services
5. Shell prompt integration showing active account
